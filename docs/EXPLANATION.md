# 解説: JMeter の性能試験で「コンテナの中」を見えるようにする

この文書は、このリポジトリで作ったもの (性能試験用メトリクス収集 `perf-metrics.sh` と Excel レポート
`New-PerfMetricsReport.ps1`) が **何をするのか・なぜ必要なのか・どういう歴史の上にあるのか** を、
専門用語を知らない人 (小学生) にも分かるように、たとえ話を交えて説明します。
各章の最後には、実際に設定・判断するための「おとな向けの要点」も書いています。

> 2026 年 10 月時点の情報です。「最新」と書いたものは、参考文献 (最後の章) の日付の情報に基づいています。

---

## 0. まず、ひとことで

**JMeter で大勢のお客さんを一度に送り込んだとき、お店 (JBoss) の「奥」で何が起きているかを、10 秒ごとにノートへ書き取り、
最後に白黒の成績表 (Excel) にまとめる仕組み** です。

### レストランでたとえると

| 本物 | レストランでいうと |
|---|---|
| JMeter | 「練習用のお客さん」を何百人も同時に送り込むロボット |
| ECS (Fargate) のタスク | ビルの中に借りた「お店の区画」 |
| コンテナ | 区画の中の「厨房」(フロントコンテナ = 受付の厨房、バックコンテナ = 奥の厨房) |
| JBoss EAP | 料理を作る「厨房のしくみ」(料理人・注文票・調理台の決まりごと) |
| Java (OpenJDK) の JVM | 厨房の「建物の設備」(ガス・水道・掃除の係) |
| DB (データベース) | 食材の「倉庫」 |
| DB 接続プール | 倉庫へつながる「電話の回線」の束 (数に限りがある) |
| CPU | 「コンロ」 |
| スレッド | 「料理人」 |
| GC (ガベージコレクション) | 「お皿洗い係」。たまに全員の手を止めて一気に片付ける |
| CloudWatch Container Insights (拡張) | お店の「外」から見るメーター (電気・水道・ガスの使用量、出入りの人数) |
| このリポジトリの収集 (①②③④) | 厨房の「中」に入って見る係 (誰が電話を待っているか、どの料理人が忙しいか、お皿洗いで止まった時間) |
| Excel レポート | 試験の「成績表」 |

外のメーター (Container Insights) を見れば「電気をたくさん使った」ことは分かります。でも、**なぜ** お客さんを待たせたのか
(倉庫への電話がふさがっていた? お皿洗いで全員止まっていた? コンロの数を間違えて料理人を雇いすぎた?) は、
厨房の中に入らないと分かりません。それをするのが、このリポジトリです。

## 1. 登場人物と、その歴史

### 1-1. JMeter ― 「練習用のお客さん」を送るロボット
- **1998 年**、Apache ソフトウェア財団の Stefano Mazzocchi さんが、Web サーバー (Apache JServ) の速さを測るために作ったのが始まりです。
- いまでは Web・API・DB などの「負荷試験」の定番の道具です。
- **たとえ**: 開店前に、ロボットのお客さんを 100 人、1000 人と送り込んで、お店がどこで詰まるかを確かめます。

### 1-2. コンテナと ECS・Fargate ― 「借りた厨房」
- **2013 年** に Docker が登場し、アプリを「コンテナ」という箱に入れて、どこでも同じように動かせるようになりました。
- **2014 年 (発表) / 2015 年 (正式提供)** に AWS が、コンテナを動かすサービス **Amazon ECS** を始めました。
- **2017 年 11 月** に **AWS Fargate** が登場し、サーバー (コンピューター) を自分で用意しなくても、コンテナを動かせるようになりました。
  Fargate のタスクは、タスクごとに分けられた小さな仮想マシン (microVM) の中で動きます
  (AWS は、2018 年に公開した Firecracker という仕組みが Lambda と Fargate を支えていると説明しています)。
  コンテナの中から見える「CPU の数」は、この microVM の CPU の数です。
- **たとえ**: ビルのオーナー (AWS) が、厨房つきの区画を「コンロ何口・冷蔵庫何リットル」という単位で貸してくれます。
  建物の管理はオーナーがしてくれるので、お店の人は料理に集中できます。

### 1-3. UBI と Red Hat build of OpenJDK ― 「厨房の建物」
- **UBI (Universal Base Image)** は **2019 年 (RHEL 8 と同時)** に Red Hat が無料で配り始めた、コンテナの土台用の Linux です。
  UBI 9.8 は **RHEL 9.8 (2026 年 5 月)** に対応する版です。
- **Java** は 1995 年に Sun Microsystems が発表し、2006～2007 年に **OpenJDK** としてオープンソースになりました。
  **Red Hat build of OpenJDK** は Red Hat が品質を保証して配る OpenJDK です。
  **Java 21** は **2023 年 9 月** に出た「長期サポート版 (LTS)」です。
- **たとえ**: 厨房を建てる「土台」と「設備」です。土台 (UBI) は軽くて、必要最小限の道具しか置いていません。
  だから、`top` や `ps` という「見回りの道具」も最初は置いていません (→ ③ で対処します)。

### 1-4. JBoss EAP ― 「厨房のしくみ」
- **1999 年**、Marc Fleury さんが始めた「EJBoss」というオープンソースが JBoss の始まりです。
- **2006 年** に Red Hat が JBoss 社を買収しました。
- **2011 年** の **JBoss AS 7** で中身がほぼ作り直され、今の **管理の仕組み (jboss-cli)**、**DB 接続プール (IronJacamar)** などが入りました。
- **2013 年** にコミュニティ版の名前が **WildFly** に変わり、**2014 年の WildFly 8** で Web サーバー部分が **Undertow** になりました。
- Red Hat が品質保証して売る版が **JBoss EAP** です。**EAP 8.0 (2024 年 2 月)** で Jakarta EE 10 (`javax` から `jakarta` への名前の引っ越し) に対応し、
  **EAP 8.1 (2025 年)** が今回の対象です。
- **たとえ**: 「注文を受ける窓口 (Undertow)」「料理人の配置 (スレッドプール)」「倉庫への電話 (DB 接続プール)」
  「注文の取り消しの約束 (トランザクション)」をまとめて受け持つ、厨房の運営マニュアルと係の人たちです。

### 1-5. EFS と readonlyRootFilesystem ― 「書き込めない壁」と「外のノート」
- **Amazon EFS (2016 年に正式提供)** は、複数のタスクから同時に使えるネットワークのファイル置き場です。
- **readonlyRootFilesystem=true** は、コンテナの中のファイル (ルートファイルシステム) を **読み取り専用** にする設定です。
  乗っ取られても書き換えられにくくする、安全のための設定です。
- **たとえ**: 厨房の壁がラミネート加工されていて、メモを書けません。だから、メモは **外に置いた共有のノート (EFS)** に書きます。

### 1-6. CloudWatch Container Insights (拡張) ― 「外から見るメーター」
- **2019 年** に Container Insights が始まり、**2024 年 12 月 2 日** に ECS 向けの **「拡張された可観測性 (enhanced observability)」** が登場しました。
  タスクやコンテナごとの CPU・メモリ・ネットワーク・ストレージの使用量、再起動の回数などを、細かく自動で集めてくれます。
- **たとえ**: 区画ごとの電気・ガス・水道のメーターと、出入りの人数のカウンターです。
- このリポジトリは、**このメーターで見えるものは集めません**。同じものを二重に集めても意味がなく、収集の負荷が増えるだけだからです。

## 2. なぜ、これが必要になったのか (経緯)

性能試験で「遅い」「エラーが出た」と分かったとき、外のメーターだけでは次のような疑問に答えられませんでした。

1. **DB への接続が足りなかったのか?** → JBoss の接続プールの中を見ないと分からない (①)
2. **GC で止まっていたのか? ヒープが足りないのか?** → JVM の中を見ないと分からない (②)
3. **CPU を使っていたのは誰か? アプリか、GC か、JIT か、収集の道具か?** → スレッドの単位で見ないと分からない (③)
4. **そもそも JVM は CPU の数を正しく分かっているのか?** → Fargate では、ここに落とし穴がある (④)

さらに、コンテナならではの制約がありました。

- **壁に書けない** (readonlyRootFilesystem=true) ので、結果を書く場所を工夫する必要がある
- **共有の「最新」看板 (mid/current) を通して書くと、別のタスクのノートを書き換えてしまう** 恐れがある
  (pin 方式で server.log を実体パスに固定したのと同じ問題)
- **本番のイメージには入れたくない** (性能試験のときだけ使いたい)
- **UBI の最小イメージには top も ps も無い**

これらを全部まとめて解いたのが、このリポジトリです。

## 3. ① jboss-cli ― 厨房の「係長」に聞き取りをする

### 3-1. 小学生向けのたとえ

厨房には「係長」(JBoss の管理窓口) がいて、「いま電話は何本使っている?」「待っている人は何人?」と聞くと、正確に答えてくれます。
**jboss-cli** は、その係長に質問する「インターホン」です。

ただし、インターホンを毎回つなぎ直すと時間がかかるので、**ずっとつなぎっぱなし** にして、10 秒ごとに同じ質問をします。

### 3-2. DB 接続プールとは

倉庫 (DB) に電話するたびに回線を引き直すと遅いので、**あらかじめ電話を何本か引いておき、使い回します**。これが接続プールです。

| 値 | 意味 | たとえ |
|---|---|---|
| InUseCount (使用中) | いま使っている接続 | 話し中の電話 |
| ActiveCount (アクティブ) | 引いてある接続 | 引いてある電話の本数 |
| max-pool-size (最大プール) | 引ける上限 (未設定なら 20) | 引ける電話の最大数 |
| WaitCount (待ち) | 空きを待った回数 | 電話が空くのを待った人 |
| BlockingFailureCount (取得失敗) | 待ちきれずに失敗した回数 (アプリでは IJ000453 などの例外) | 待ちきれずに帰ったお客さん |
| 平均待ちスレッド数 (このレポートで計算) | 待ち時間の合計 ÷ 経過時間 | 「平均して何人が電話の前に並んでいたか」 |

### 3-3. ほかに聞くこと

- **HTTP リスナー**: 何件の注文を受けたか、何件エラー (500) だったか
- **IO ワーカー**: HTTP の注文を処理する料理人 (default task-N) が何人働いているか、上限は何人か、列に並んだ注文はあるか
- **EE / EJB スレッドプール**: 裏方の料理人のチーム
- **セッション**: お客さんごとの「伝票」がいくつあるか (伝票は片付けるまでヒープを使う)
- **トランザクション**: 「全部やるか、全部やめるか」の約束がいくつ成功・中断・時間切れになったか
- **JVM**: 料理人 (スレッド) の数、ヒープの使用量、サーバーの状態

### 3-4. おとな向けの要点

- 統計はふだん無効なので、起動引数に `-Dwildfly.datasources.statistics-enabled=true`・`undertow`・`transactions` を足します
  (WildFly 系の標準の設定ファイルは `${wildfly.<サブシステム>.statistics-enabled:${wildfly.statistics-enabled:false}}` で受け取る)。
  それでも無効なデータソースは、実行時に統計だけを有効化します (設定ファイルは変えません)。
- jboss-cli は **1 つだけ常駐** させ、FIFO で命令を送り、返ってきた DMR (JBoss の管理データ形式) を awk で CSV にします
  (busybox の awk でも動くように書いています)。
- 応答しなかった回 (JBoss の高負荷・長い GC 停止・停止中) も、`cli_jvm.csv` に「応答 0」として OS のスレッド数だけ記録します。
- Undertow の送受信バイト数は Container Insights のネットワーク転送量と重なるので取りません。
  処理時間はリスナーの `record-request-start-time=true` のときだけ値が入ります (既定は false。応答時間は JMeter で見る)。

## 4. ② jstat・jcmd・JFR ― 建物の「健康診断」と「ブラックボックス」

### 4-1. 小学生向けのたとえ

- **jstat** は「体温計」です。10 秒ごとに、ヒープ (料理を置く台) がどれだけ埋まっているか、お皿洗い (GC) を何回したかを測ります。
- **jcmd** は「お医者さんの健康診断」です。1 分ごとに、もう少し詳しく (台の区画の使い方、レシピ帳の置き場、料理人がそれぞれ何をしているか) を調べます。
- **JFR (Java Flight Recorder)** は、飛行機の **ブラックボックス (フライトレコーダー)** から名前をとった記録装置です。
  厨房の出来事をずっと録画しておき、あとから「いつ・誰が・どこで止まっていたか」を巻き戻して見られます。

### 4-2. 歴史

| 年 | 出来事 |
|---|---|
| 2004 | J2SE 5.0 に **jstat** (jvmstat という計測の仕組み) が入る |
| 2008 | Oracle が BEA を買収。BEA の JVM「JRockit」に **Flight Recorder** があった |
| 2011 | JDK 7 に **jcmd** (JVM に命令を送る万能の道具) が入る |
| 2013 | Oracle JDK 7u40 に JFR が入る (このときは有償の機能) |
| 2017 | JDK 9 で **G1 GC** が標準になる |
| 2018 | **JDK 11 で JFR がオープンソースに** (JEP 328)。誰でも無料で使えるようになった |
| 2020 | JDK 8 (8u262) にも JFR がバックポートされる |

### 4-3. 何が分かるか

| 道具 | 主に見るもの | 「こうなっていたら注意」 |
|---|---|---|
| jstat (`-perfgc`) | ヒープ各領域、GC の回数と時間、**直近の GC の原因**、セーフポイント (全員の手を止める時間)、JIT の時間、スレッド数、クラス数 | Full GC がある / GC 時間率 5% 以上 / Old が最大ヒープの 85% 以上 |
| jcmd GC.heap_info | G1 の区画 (リージョン) の使い方、メタスペース、クラス空間 | ― |
| jcmd Compiler.codecache | JIT が作った「速いレシピ」の置き場 (コードキャッシュ) | 満杯になると JIT が止まって遅くなる |
| jcmd Thread.print | 料理人 (スレッド) が何をしているか。**DB の電話待ちの料理人** も数える | DB 接続待ち・ロック待ちが多い |
| jcmd VM.native_memory | JVM がヒープ以外に使っているメモリ (`PERF_NMT=summary` のとき) | 増え続ける分類がある |
| JFR | GC ごとの停止時間、CPU を使ったメソッド、ロック待ちの場所、I/O 待ち、例外の数 | 1 回の GC 停止が 200 ms 以上 / 例外が毎秒 100 件以上 |

### 4-4. おとな向けの要点

- Red Hat の OpenJDK 21 の runtime イメージには `jstat` のコマンドがありません。そこで **`java -m jdk.jcmd/sun.tools.jstat.Jstat`** として呼び、
  さらに **カスタムの表示オプション (`perfgc`)** を `~/.jvmstat/jstat_options` に置いて、1 つの常駐プロセスで多くの列を取ります。
- JFR は **JBoss の起動時から** 記録します (`-XX:StartFlightRecording`。統計のイベントだけ `jdk.CPULoad#period=10s` のように間隔を指定)。
  JVM のオプションは `PREPEND_JAVA_OPTS` で渡します。`JAVA_OPTS` を空から設定すると standalone.conf の既定値 (`-Xms` / `-Xmx` など) が効かなくなるためです。
- 記録は `perf/jfr/` に残り (JBoss の終了時に `perf_<pid>_<日時>.jfr`)、`perf-metrics.sh jfr-csv` で CSV にします。
  変換は単一ファイルの Java (`PerfJfrCsv.java`) を JVM で直接実行するので、追加のツールは要りません。
- jstat / jcmd は **`/tmp` が書き込めないと JVM に接続できません** (hsperfdata とアタッチ用のソケットを使うため)。
  readonlyRootFilesystem=true では `/tmp` にボリュームを当て、**フロントとバックで別のボリューム** にします (共有すると PID が重なり、別の JVM を読みます)。

## 5. ③ top・ps・/proc ― 「見回り係」

### 5-1. 小学生向けのたとえ

- **ps** は「出席簿」です。いま厨房にいる人 (プロセス) の一覧を作ります。
- **top** は「見回り係」です。いま一番忙しい人は誰か、コンロ (CPU) をどれだけ使っているかを数えて回ります。
- **/proc** は、Linux が用意している「先生だけが見られる名簿」のようなものです。top も ps も、実はこの名簿を読んでいます。

### 5-2. 歴史

- **ps** は 1970 年代の UNIX から、**top** は 1984 年に William LeFebvre さんが作ったのが始まりです。
- **/proc** は 1984 年の UNIX (第 8 版) で生まれ、Linux にも 1990 年代のはじめから入っています。

### 5-3. 何が分かるか (Container Insights では見えないもの)

- **プロセス別** の CPU: JBoss・収集の道具 (jboss-cli・jstat・jcmd・perf-metrics)・その他
  → **このレポートのための収集が、どれだけ CPU を使ったか** も分かります (結合試験では平均で 1 コアの 1.7%)
- **JBoss のスレッドの用途別** の CPU: HTTP 処理・HTTP I/O・GC・JIT・JBoss 内部・JFR など
  → 「CPU を食っていたのはアプリか、お皿洗い (GC) か、レシピの勉強 (JIT) か」
- **CPU が高いスレッドの上位 10 件** (名前と TID。スレッドダンプの nid と突き合わせられる)
- **ファイル記述子の数**、**TCP の接続** (受信側・送信側・CLOSE_WAIT・TIME_WAIT と相手のポート)
- **非自発的なコンテキストスイッチ** (仕事の途中でコンロを取り上げられた回数。多いと CPU 不足)

### 5-4. おとな向けの要点

- UBI の最小イメージには procps-ng (top・ps) がありません。ビルド引数 `PERF_PROCPS=auto` で導入を試み、
  **導入できなくても /proc を直接読んで同じ項目を算出** します (結合試験はこの代替経路で行いました)。
- スレッド名は Linux の制限で 15 文字まで (`C2 CompilerThre` など) です。用途の分類はこの名前で行います。

## 6. ④ `-XX:ActiveProcessorCount` ― 「コンロの数を正しく教える」

ここが、Fargate で Java を動かすときの **いちばんの落とし穴** です。

### 6-1. 小学生向けのたとえ

ビルのオーナー (AWS) は、1 つの大きな建物 (microVM) にコンロを 4 口つけています。
でも、あなたのお店 (コンテナ) が使ってよいのは **「4 口のうち 0.5 口ぶん」** です。

ただし、オーナーはコンロに鍵をかけません。「ほかのお店が使っていなければ、空いているコンロを使ってもいいよ。
でも混んできたら、**使ってよい割合 (シェア)** に合わせて分け合ってね」というルールです。

ところが、厨房の店長 (JVM) は、建物にあるコンロの数 (4 口) を見て、**「コンロが 4 口あるなら、料理人を 4 口ぶん雇おう」** と考えます。
お皿洗い係 (GC スレッド) も 4 人、レシピを勉強する係 (JIT) も 3 人、注文窓口 (Undertow の I/O) も 8 人、注文係の上限は 64 人……。

混んでくると、本当は 0.5 口ぶんしか使えないので、**大勢の料理人がコンロの取り合いになり、かえって遅くなります**。

そこで、店長に「うちのコンロは 1 口ぶんだよ」と **教えてあげる** のが、`-XX:ActiveProcessorCount=1` という設定です。

### 6-2. なぜこうなったのか (歴史)

| 年 | 出来事 |
|---|---|
| 2006～2008 | Google の技術者が「プロセスのグループ」を作り、**cgroups** として Linux 2.6.24 (2008 年 1 月) に入る。コンテナの土台 |
| 2012 | Linux 3.2 で、CPU を **上限 (クォータ)** で縛る仕組み (CFS バンド幅制御) が入る。ほかに **シェア (取り分の比率)** という分け方もある |
| 2016 | Linux 4.5 で cgroup v2 |
| 2018 | **JDK 10 で JVM がコンテナを理解する** ようになる (cgroup の上限から CPU 数とメモリを決める。`-XX:ActiveProcessorCount` もこのとき追加。JDK 8u191 にも) |
| 2018 | Linux 4.20 で **PSI** (CPU などを「待った」時間の割合) |
| 2022 | **JDK-8281181**: 「CPU シェアを CPU 数の計算に使わない」に変更 (JDK 19。17.0.5・11.0.17・18.0.2 にもバックポート)。シェアは「上限」ではなく「混んだときの比率」なので、Kubernetes などで CPU を使い切れない問題があったため |
| 2023 | JDK 21 (LTS)。元に戻すオプション `UseContainerCpuShares` は JDK 21 で削除 (この環境でも「認識できないオプション」になることを確認) |
| 2026-07 | AWS のブログが「Fargate は CPU をシェアで配分し、クォータを使わない。JVM はホスト (microVM) の CPU 数にフォールバックする。`-XX:ActiveProcessorCount=N` をタスクの vCPU に合わせよ」と案内 |

つまり、**JVM の側は正しい理由で変わったのに、Fargate の「上限ではなくシェアで配る」やり方と組み合わさると、JVM が CPU を多く見積もる**
という「すれ違い」が起きているのです。

### 6-3. このリポジトリの判定のしかた

1. **ECS タスクメタデータ v4** (2020 年の Fargate プラットフォーム 1.4.0 から使える「お店の契約書」) を読み、
   **このコンテナの取り分** を求めます。
   - コンテナ定義に `cpu` (CPU ユニット。1024 = 1 vCPU) があれば、それ ÷ 1024
   - 無ければ、タスクの vCPU ÷ JVM を動かすコンテナの数 (サイドカーは名前・イメージで除外)
2. **JVM が認識した CPU 数** を、jcmd (VM.info・VM.flags) と jboss-cli (available-processors) で調べます。
3. さらに、オプション無しの新しい JVM を 1 回だけ起動して、**このコンテナで JVM が何を選ぶか**
   (`-XshowSettings:system`・`-Xlog:os+container`) も記録します。
4. 比べて判定します。

| 判定 | 意味 |
|---|---|
| **要** | JVM の CPU 数 > 取り分 → `-XX:ActiveProcessorCount=<取り分 (四捨五入・最小 1)>` を推奨 |
| 要検討 | JVM の CPU 数 < 取り分 (増やせる) |
| 不要 | 一致 |
| 設定済み | すでに指定済み (タスクの vCPU を超えていれば「要確認」) |
| 判定不可 | 取り分や CPU 数が分からない |

5. **試験中の実測** で裏付けます (レポートの「④CPU判定」「④CPUスケジューリング」シート)。
   - JBoss の CPU 使用量 (コア) と取り分の線を同じグラフに描く
   - GC・JIT が使った CPU、実行を待っているスレッドの数、非自発的なコンテキストスイッチ、steal、PSI

### 6-4. 結合試験での実例

タスク 1 vCPU・コンテナ 512 ユニット (= 取り分 0.5 vCPU) の偽のメタデータで試したところ、

- JVM は CPU を **4 個** と認識 (VM の CPU 数そのまま)。ParallelGCThreads=4、CICompilerCount=3、IO スレッド 8、タスクスレッドの上限 64
- 判定は **「要」→ `-XX:ActiveProcessorCount=1`**
- 試験中、JBoss は 95% 値で 1.41 コアを使い、取り分 (0.5) を超えていました (ほかのコンテナが暇だったので使えただけ)。
  実行を待つスレッドが CPU 数を超える時間もありました

### 6-5. おとな向けの要点

- 指定する場所は JBoss の JVM オプションです。タスク定義の環境変数 `PREPEND_JAVA_OPTS` に `-XX:ActiveProcessorCount=1` を足すのが簡単です
  (standalone.sh が JAVA_OPTS の前に足す。JAVA_OPTS 自体を環境変数で丸ごと設定すると、standalone.conf の既定値が使われなくなる)。
- 取り分が 1 未満でも、推奨は最小 1 です。**CPU 1 と判定されると、JVM は自動で Serial GC を選びます** (「2 CPU 以上かつメモリ 1792MB 以上」がサーバー級の条件)。
  G1 を使い続けたい場合は `-XX:+UseG1GC` を明示するか、`ActiveProcessorCount=2` を検討します (判定のメッセージにも出ます)。
- 指定したあとは、**同じ JMeter のシナリオでもう一度試験** し、スループット・応答時間・GC の停止が良くなったかを比べてください。

## 7. 結果をどこに書くか ― 「外のノート」と「自分のページ」

### 7-1. 小学生向けのたとえ

壁に書けない厨房なので、外に置いた共有ノート (EFS) に書きます。ノートには、**お店ごと・開店した日ごとのページ** (`mid/<LOG_ID>`) があります。
「いちばん新しいページ」には **しおり (current)** がはさんであります。

でも、しおりは **全部のお店で 1 本を共有** しています。別のお店が開店すると、しおりがそちらのページに移ります。
しおりのページに書き続けると、**いつのまにか別のお店のページに書いてしまう** ことがあります。

だから、**開店したときに自分のページ番号を覚えておき、そのページに直接書きます** (これを「pin = ピンで留める」と呼んでいます)。

### 7-2. 実際の場所

```
/mnt/logs/<Component_name>/logs/<Service_Name>/mid/<LOG_ID>/perf/
  例) /mnt/logs/front/logs/intra-web/mid/20261024141140-6jlezcax/perf/
  (最後に開店したお店のページは /mnt/logs/front/logs/intra-web/mid/current/perf/ から辿れる)
```

作業用の小さなファイル (jboss-cli とやりとりする FIFO など) は、書き込める `/tmp` に置きます。

## 8. 「1 ファイル」と「ビルド引数」― 本番に持ち込まないしくみ

### 8-1. 小学生向けのたとえ

性能試験の道具は **1 つの道具箱 (`perf-metrics.sh`)** にまとめてあります。
お店を建てるとき (ビルド) に「今回は試験用だよ (`PERF_METRICS_ENABLED=true`)」と言えば道具箱を置き、
言わなければ (既定の `false`) **道具箱を捨てて、本番と同じ厨房** にします。

開店のとき (起動) には、入口の係 (エントリポイント) が「道具箱はある? 試験用?」を確かめ、
試験用なら **「性能試験用メトリクス収集: 有効」** と大きく貼り紙をして (起動ログの枠)、道具を動かし始めます。

道具箱がうまく動かなくても、**お店の開店は止めません**。

### 8-2. おとな向けの要点

- エントリポイントへの追加は「6-B」の 1 か所だけです。`.` で perf-metrics.sh を読み込み、`perf_metrics_start` を呼び、
  standalone.sh の引数に統計の有効化を、`PREPEND_JAVA_OPTS` に JFR・NMT を足します。
- 収集は別のプロセスで行い、JBoss の起動を待たせません (JBoss の JVM と管理窓口が現れるのを待ってから取り始めます)。
- 既存の試験 333 件が、変更前・変更後とも合格しています (= 試験用の追加が、もとの動きを変えていない)。

## 9. Excel レポートの読み方 ― 「成績表」

### 9-1. 小学生向けのたとえ

試験が終わったら、ノートの内容を **白黒の成績表** にまとめます。
いちばん前のページ (サマリー) には、先生のコメント (所見) が **大事な順** に並びます。

| 印 | 意味 |
|---|---|
| ■ 要対応 | すぐ直したほうがよいこと (接続の取得失敗、Full GC、1 秒以上の停止、ActiveProcessorCount「要」など) |
| ▲ 注意 | 気をつけたいこと (接続待ち、上限到達、GC 時間率 5% 以上、CPU 不足など) |
| ● 参考 | 知っておくとよいこと (収集の負荷、セッションの作りすぎ、TIME_WAIT の多さなど) |
| ○ 良好 | とくに問題なし |

### 9-2. 見る順番のおすすめ

1. **サマリー** の所見と ④ の判定を読む
2. **グラフ** で、JMeter の負荷をかけた時間帯に何が起きたかを見る (全グラフの時間軸は同じ)
3. 気になったところを **各シート** で数字で確かめる (4 行目が分類、5 行目が見出し、6 行目が元の CSV の列名。フィルター付き)
4. 原因の場所を **②JFR上位** (ロック待ち・CPU を使ったメソッド) と **②スレッド状態**・**③topスレッド** で探す
5. **④CPU判定** で、CPU の数の設定が合っているかを確かめる

### 9-3. ファイル名

ノートのページの場所 (`/mnt/logs/<front|back>/logs/<サービス>/...`) から、**どのお店のどの厨房の成績表か** をファイル名に入れます。

```
perf_report_フロントコンテナ_intra-webサービス_20261024141140-6jlezcax.xlsx
perf_report_バックコンテナ_intra-apiサービス_20261024141140-6jlezcax.xlsx
```

`intra-web-front`・`interapi-back` のように末尾が front / back の名前や、`interapi`・`sfapi`・`sf_api` のような表記ゆれも、
`フロントコンテナ`・`inter-apiサービス`・`sf-apiサービス` のようにそろえます。

### 9-4. おとな向けの要点

- Excel が無い PC でも作れます (Office Open XML を直接書く)。Windows PowerShell 5.1 でそのまま動きます
  (日本語を含むプログラム本体は、文字コードに左右されない読み込み方をしています)。
- 時刻は既定で PC のタイムゾーンに換算します (JMeter の結果と突き合わせるため)。`-From` / `-To` で試験の時間帯に絞れます。
- JFR の CSV が無いときは、`-ConvertJfr` で PC の JDK (17 以降) を使って変換できます
  (入力に含まれる変換プログラムが perf-metrics.sh 3.0.0 のものと一致するときだけ実行します)。

## 11. 用語集

| 用語 | ひとことで |
|---|---|
| ヒープ | Java のオブジェクトを置く「調理台」 |
| GC (ガベージコレクション) | 使い終わったオブジェクトを片付ける「お皿洗い」。全員の手を止める時間 (停止) がある |
| Young / Old / Full GC | 新しい物だけ / 古い物も / 全部を片付けるお皿洗い |
| G1 | 調理台を小さな区画 (リージョン) に分けて少しずつ片付ける GC。JDK 9 からの標準 |
| メタスペース | クラス (レシピの型) の情報を置く場所 |
| JIT / コードキャッシュ | よく作る料理を「速いレシピ」に書き直す係 / その置き場 |
| セーフポイント | JVM が全員の手を止める合図 |
| スレッド | 料理人。同時に動ける仕事の単位 |
| スレッドダンプ | 全員が「いま何をしているか」の一斉調査 |
| コンテキストスイッチ | コンロを別の料理人に交代すること。非自発的 = 途中で取り上げられた |
| CPU シェア / クォータ | 混んだときの取り分の「比率」 / 使ってよい「上限」 |
| steal | 同じ建物のほかの VM にコンロを取られた時間 |
| PSI | コンロを「待った」時間の割合 |
| ファイル記述子 (FD) | 開いているファイルや接続の「受付番号」 |
| CLOSE_WAIT / TIME_WAIT | 相手が切ったのにこちらが閉じていない接続 / 閉じた後のしばらくの待ち |
| 95% 値 | 小さい順に並べて 95% の位置の値。「たまの最大」に引きずられない「ほぼ最大」 |
